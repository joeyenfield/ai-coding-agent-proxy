# Authentication and authorization

Read this before changing credentials, permissions or routes. Authentication is mandatory, including loopback and an empty account store; there is no no-accounts mode and no code for one. The permission helpers (`access.can_view`/`can_control`/`is_owner`, `fleet.owns`/`allowed`/`can_manage`/`removed_for`, `mcp.usable`) still accept `Identity | None`, but `None` is denied everything: **no protected HTTP or WebSocket handler may receive an anonymous identity**, and none does (the middleware sets one; `routes/mcp.py` and `intercept.py` check for `None` before asking).

## Boundaries

- `issuer.py` runs **agent-auth** (`create_auth_app`, console script `agent-auth`, `127.0.0.1:10000` unless `AI_PROXY_AUTH_HOST`/`AI_PROXY_AUTH_PORT`), a separate Authlib OAuth/OIDC issuer at `https://auth.aicontrolmesh.com` (`AI_PROXY_OIDC_ISSUER`). It is never mounted into the API app. It reads existing accounts through `UserStore(db, readonly=True)` but never writes them. Credentials, grant transactions and signing material are its own state (`issuer.State`), in the database `state_database` picks: `AI_PROXY_AUTH_DATABASE_URL`, else the API's PostgreSQL URL, else a SQLite file `issuer-state.sqlite3` in its state folder (`AI_PROXY_OIDC_STATE_DIR`, else `oidc/` in the account-state folder). On PostgreSQL that state is schema `mesh_auth`, owned by role `mesh_auth`, which can read only `mesh.users`, `mesh.orgs` and `mesh.meta` (`migrate.grant_issuer`, run when the API migrates; `ISSUER_READS`), and `accounts_database` reads accounts through that same connection. On SQLite it opens the API's file read-only. It calls `Settings.load(database=False)`: it needs only the environment. It refuses to start without `AI_PROXY_OIDC_INTROSPECTION_SECRET`.
- Built-in clients (`Issuer.client`): the console (`mesh-console`: authorization code + refresh, only the registered redirect URIs), the CLI (`mesh-cli`: device code + refresh) and the API's introspection client (`mesh-api`: no grants). Service clients (`client_credentials`) are rows in the issuer's `records` table, added with `agent-auth client add <id> --user <name>` and removed with `agent-auth client remove <id>`.
- `auth.py` runs the API resource boundary. `Auth.identify` uses a dedicated, proxy-free httpx client to introspect opaque access tokens at `<issuer>/introspect` with the confidential API client's secret. The middleware runs it in a thread, not on the ASGI loop. Failure or a missing secret raises `AuthUnavailable` (503), never anonymous fallback.
- `routes/auth.py` is the browser BFF: Authlib discovery, authorization code + S256 PKCE, state/nonce and ID-token validation, access/refresh cookies, renewal and revocation. Passwords are submitted only to the issuer. The old password, launcher-token and password-change routes (`POST /api/auth/login`, `/api/auth/token`, `/api/auth/tokens*`, `/api/auth/password`) answer 410.
- `access.py`, `fleet.py` and route helpers retain existing roles, session sharing and per-machine feature grants. The issuer does not replace authorization or assign privileges from untrusted claims.
- `remote.py` trusts only the middleware identity (`RemoteAccess.trusted`). Loopback and the legacy access key confer no API access, and the key file is no longer created. Pairing is gone: `GET /api/remote` only reports status (`trusted`, with `local`/`paired` always false and `accounts` always true), `POST /api/remote/code` and `/rotate` answer 403 for everyone, `/pair` 410, and `/unpair` only clears the old cookie (`remote.COOKIE`). These tombstones stay so old consoles and scripts get a clear refusal.

## Credentials

| Credential | Transport | Persistence and validation |
| --- | --- | --- |
| Account password | Issuer's CSRF-bound sign-in forms | scrypt hash in the `users` table. Issuer uses `Auth.check_password` and its own in-memory rate limits (`Issuer.rate`). `AI_PROXY_USERNAME`/`AI_PROXY_PASSWORD` define one more account, an admin, kept outside the database (`Auth.environment_user`). |
| Access token | `Authorization: Bearer`, `X-AI-Proxy-Token`, or API cookie `ai_proxy_session` | Opaque, five-minute token; issuer stores only its hash. API validates active, issuer, audience, `mesh-api` scope, Bearer type, expiry and current account identity. An ID token is not accepted. |
| Refresh token | Token endpoint; browser cookie `mesh_accounts`, path `/api/auth` (signed with the `oidc-browser-key` secret; one refresh token per account the browser is signed in to, up to `MAX_ACCOUNTS` (5), and which is active; an older single `mesh_refresh` is read once and moved into it) | Hash at issuer, rotating, absolute 30-day family lifetime; replay revokes the family, except one retry within `REFRESH_REUSE_GRACE` (60 s) of first use (`used_at`, `reused`), for a client whose answer was lost. CLI stores local credential secrets with restricted permissions and cross-process refresh serialization. |
| ID token | Code exchange only | RS256, discovery/JWKS, client audience and nonce; verified by Authlib, never an API credential. |
| Service-client secret | HTTP Basic to `/token` | Explicitly provisioned client bound to an existing member account, never an admin (`Issuer.provision`). Hash at issuer. Its tokens stop working once that account changes password, is recreated or becomes an admin (`Issuer.active`). |
| API introspection secret | HTTP Basic to `/introspect` | Shared secret through environment/secret manager, never the stored settings. This resource client cannot mint service-account tokens. |
| Session id / MCP capability | Agent paths and MCP launch URL | Session id selects the session, not an authentication bypass. MCP additionally requires its launch-only hashed capability and current machine grant. |

Issuer transactions (`State.transaction`) cover grant validation, consumption and token persistence: one at a time in the process, and across processes PostgreSQL's advisory lock or SQLite's `BEGIN IMMEDIATE`. Each record is a `(kind, key)` row with its JSON `data` and an `exp` column, so expired records are cleaned up by an indexed delete. The signing key is the secret `signing-key` in the issuer's own `secrets` table; its SQLite file is owner-only. `Auth.account_version` binds tokens to the digest of the account's `created_at` (a float) and password hash (the environment account's to its password); reset, deletion and same-name recreation invalidate credentials, and anything that stores, imports or copies users must keep both exactly. Current role, organizations and teams are reloaded at the API boundary (`Auth.identity_for`). `UserStore` keeps the whole directory in memory and re-reads it when meta `accounts_version` changes (checked once per call), so changes by `agent-server user`, another server process or the API reach the issuer at once. Old versions' browser sign-ins and launcher tokens (`users.json`'s `sessions` and `tokens`) are not imported into the database; nothing authenticates with them (tests make look-alikes with `oidc_helpers.plant_legacy_credentials`).

## Request pipeline

1. `VersionMiddleware` rejects unsupported protocols (426 / WebSocket 4426). Protocol 2 (`MIN_PROTOCOL` = `PROTOCOL` = 2) removes legacy authentication.
2. Only `PROTECTED_PREFIXES` (`/api/`, `/v1/`, `/anthropic/`, `/session/`, `/docs`, `/redoc`, `/openapi.json`) go through `AuthMiddleware`; the console, `/help-files/`, `/downloads/` and the installers stay public outside them.
3. On those, it checks Origin (`remote.same_origin`) on unsafe methods and every WebSocket before anything else, public paths and machine tunnel callbacks included. Exact API origin or `console_origins` only; no parent-domain cookies. Native clients may omit Origin.
4. `PUBLIC_PATHS` may run unsigned: `/health`, `/api/auth/status`, `/api/auth/login`, `/api/auth/callback`, `/api/auth/refresh`, `/api/auth/logout`, `/api/auth/accounts`, `/api/auth/switch` (the last two read and change only the browser's own `mesh_accounts`). `/api/auth/status` still introspects a credential it is sent, and answers 503 when it can't.
5. Every other protected path requires an introspected access token: `X-AI-Proxy-Token`, else `Authorization: Bearer`, else the `ai_proxy_session` cookie. No token is 401 / 4401; unavailable issuer is 503 (on a WebSocket `_deny` closes with 4400 + status % 100, so 4403).
6. HTTP requests matching `SITE_ADMIN_ONLY` need a site admin, and those matching `ADMIN_ONLY` an admin of some organization (403); the route checks which. A `/session/<id>/...` path, or `/v1/` and `/anthropic/` with `X-AI-Proxy-Session`, additionally needs an open session the identity `access.can_control`s, else 404. The identity is put in `scope["state"]` (`auth.request_identity`).
7. Handlers check session visibility/control or machine feature grants. Hidden sessions and machines answer 404.

WebSockets revalidate credentials every 15 seconds (`CREDENTIAL_CHECK_INTERVAL`) and close 4410 for renewal/revocation, a different user or issuer failure. Terminal routes also check credentials and memberships before input/output and when idle. Live SSE checks the credential every `LIVE_RECHECK_SECONDS` (15 s) and visibility on every event; terminal viewers every `IDENTITY_RECHECK_SECONDS` (5 s), memberships and sharing on every event. `Auth.recheck` (open connections' rechecks; a new request always uses `identify`, so a sign-out applies at once) reuses the issuer's answer per token digest for `INTROSPECTION_CACHE_SECONDS` (10 s; tests set 0), and, when introspection fails, both accept a token it confirmed until that token's `exp` instead of raising `AuthUnavailable` (a new or expired token still fails closed). Reconnecting clients must renew before dialing. Sockets opened by agent-machine, agent-proxy and the console's terminal viewer (`routes/terminals.py` view, after each renewal) renew in place instead, and `Auth.recheck` follows a socket's `RENEWED_TOKEN`: the fleet socket, machine tunnels (`TunnelHub.renew`), HTTPS tunnels (`InterceptProxy.serve_tunnel(renew)`) and terminal hosts (`routes/terminals._renewal`) take `{"type": "token"}` text frames, and `auth.renew_socket` accepts one only if the issuer says it's valid and it's the same user in the same tenant; later checks use it (`RENEWED_TOKEN` in the scope). The senders re-send the current token every 60 s, so a renewal the server couldn't check is tried again.

## Signed access tokens

With `AI_PROXY_AUTH_JWT_ACCESS_TOKENS=1`, `issuer.Server.issue` signs access tokens (`Issuer.access_jwt`: RS256 with the issuer's key, `typ: at+jwt`, claims `iss`, `aud`, `sub`, `username`, `client_id`, `scope`, `iat`, `nbf`, `exp`, `jti`, `acct` (the account version), `fam` (the refresh family: `issue` picks it, `save_token` pops `_family` so it never reaches the client; a refresh grant's user carries its family)). The access record is still saved, so introspection keeps working. Revocations (`/revoke`, a reused refresh token, `agent-auth client remove`) go through `Issuer.revoked`: a shared key `revoked:<family|client>:<id>` holding when, and an `auth.revoked` message.

The API checks a signed token itself (`Auth.verify_jwt`) only when `Auth.revocations` is set (several processes) and `Revocations.fresh()` (read from the shared keys within `REVOCATIONS_STALE_SECONDS`); otherwise, or when the JWKS can't be fetched, it introspects. Accepted only with: RS256, `at+jwt`, a known key (`_keys`, refetched at most every `JWKS_REFRESH_SECONDS`), the issuer and audience, `exp`/`nbf` within `JWT_SKEW`, `mesh-api` in scope, family and client not revoked since `iat`, and `acct` equal to `account_version(username)`; then `identity_for` reads permissions fresh. **Must never**: accept a token for its signature alone, take the algorithm from the token, or skip any of these checks. With Redis, the issuer's `rate` counts in shared fixed windows.

## Browser and native clients

- **Several sign-ins per browser** (`routes/auth.py`): a sign-in adds its account to `mesh_accounts` and makes it active (the same account again replaces, and revokes, its older refresh token). `POST /api/auth/switch` renews another held account's access token into the access cookie; `POST /api/auth/logout` revokes the active account, a named one or all of them, and the next one left becomes active. Every request still carries exactly one identity, the active account's, so authorization and tenancy are unchanged. A held sign-in the issuer refuses is dropped from the cookie. The issuer keeps no sign-in session of its own, so adding an account always shows its form. The console reloads on a switch (and tells its other tabs, `BroadcastChannel` `mesh-account`), since streams, terminals and queries belong to the old account.

- Browser authorization callbacks and return origins use exact allowlists (`oidc_redirect_uris`, `oidc_browser_origins`; `Settings.__post_init__` refuses wildcards and non-HTTPS outside loopback). Signed `mesh_oidc_state` (Starlette `SessionMiddleware`, keyed by the `oidc-browser-key` secret in the database, made on first use) lasts ten minutes; access and refresh cookies are HttpOnly, host-only, SameSite=Lax and Secure for HTTPS deployments. The console never stores OAuth tokens in localStorage; it does hold its current access token in memory (`/api/auth/status` and `/api/auth/refresh` return it as `access_token`), to renew its open sockets in place. Auth status refresh is fail-closed; refreshes are serialized within a tab and with Web Locks across tabs (on plain HTTP, which has no Web Locks, a lease in localStorage), and a tab skips one another tab made after its own request was sent (`mesh-access-renewed`), so tabs never present one refresh token together (a second reuse revokes the family). The console renews ahead of expiry, a minute before or at 80% of the lifetime (`/api/auth/status` and `/api/auth/refresh` report `expires_in`), so its streams and terminals reconnect onto a fresh cookie when the server closes them at the old token's expiry.
- `agent login` and `agent-machine login` use discovery and device authorization; each owns its credentials. Refresh happens before authenticated requests and WebSocket reconnects, `RefreshBefore` (120 s) ahead of expiry. A refresh the issuer couldn't answer (down, 5xx, timeout) keeps the stored token while it has `StillValid` (30 s) left and isn't retried for `RefreshRetry` (15 s) in that process, since it may have consumed the refresh token; a timed-out credentials lock also falls back to a still-valid stored token. Only `invalid_grant` clears credentials and means login. The agent-proxy answers a token failure 401 only for `ErrLoginRequired`, else 503. A rotated token that can't be saved is retried ten times. Relays reject (on 4410) the token they last sent, not the one they dialled with. Logout revokes credentials and reports failures.
- The issuer's forms need `Origin` equal to the issuer. Keep its `Referrer-Policy` at `same-origin` (under `no-referrer` browsers post `Origin: null`) and the redirect URIs' and console origins (`oidc_browser_origins`) in its CSP `form-action` (browsers apply it to every redirect after the post: to the callback, then the callback's redirect to the console; without the console the form just sits there, signed in, and a second click finds the transaction expired). TestClient sets `Origin` by hand and can't catch either; `quickstart/tests` runs them against a real stack.
- Each issuer form has its own transaction and its own cookie (`Issuer.transaction_cookie`: `__Host-mesh_auth_transaction_<first 16 of its digest>`), so two sign-in pages at once (tabs, the console starting over) don't break each other. One shared cookie did, as `invalid_transaction` on the older page. A transaction is spent (`Issuer.finish`) only by a completed sign-in or device decision; a wrong password or code shows the same form again (`issuer_pages`), with what was typed except the password.
- People see `/authorize` and `/device` in a browser, so `IssuerError` there renders `issuer_pages.problem` (branded HTML with a way to start over: the console, or `/device`) at the same status; every other issuer endpoint keeps JSON OAuth errors. The pages have no scripts; their stylesheet is `/sign-in.css` (CSP `style-src 'self'`). The API's `/api/auth/login` and `/api/auth/callback` likewise never show JSON to a browser: a failure redirects to the console with `?sign_in=failed|unavailable`, which `Login.tsx` explains.
- A signed-in console can decide a device code without the password: `ApproveDevice.tsx` → `POST /api/auth/device` → `Auth.device_decision` → the issuer's `POST /device/console`, authenticated as the introspection client with the person's access token, which must be a console (`oidc_console_client`) token. It records the same `approval` the `/device` form does. Codes are typed by hand, never taken from a link, and `check` shows what asked before anything is decided: one-click approval is otherwise easier to phish than a password.
- **Setup codes** approve device codes without anyone at the computer: `routes/auth.py` `/api/auth/setup-codes` → `Auth.setup_codes` → the issuer's `POST /setup-codes` (same introspection-client + console-token rule as `/device/console`; actions `create`, `list`, `revoke`). A code (`msc_` + 24 random bytes) is shown once; the issuer keeps `setup_code` records by its digest (`user`, `version`, `uses` left, `exp`) and a per-person `setup_index` for listing. Limits: `SETUP_DEFAULT_LIFETIME` 1 h, `SETUP_MAX_LIFETIME` 24 h, `SETUP_MAX_USES` 100, `SETUP_MAX_ACTIVE` 20 per person. The program that asked for a device code (`mesh-cli` only) presents it at `POST /device/setup` with its `user_code`; in one transaction the issuer checks the code (unexpired, uses left, `bound_user` with its version, so a new password ends it), records the same `approval` the `/device` form does as the code's owner and spends a use; the program then polls `/token` as usual. Wrong codes count towards a per-address limit (20/600 s); right ones don't, so a firm's machines behind one address can share one. What a machine switches on (`--enable`, `AI_PROXY_MACHINE_ENABLE`) is the machine's own choice, never carried by the code.
- Device approval and denial on the issuer's own page require its CSRF-bound sign-in form. Either decision consumes the browser transaction and fixes the code's decision; denied codes return `access_denied` and cannot be approved later.
- The agent-proxy signs **all** API-bound traffic with `X-AI-Proxy-Token`, including model/MCP requests; it strips caller-supplied platform headers and browser cookies/Origin. Its loopback Host/Origin checks remain essential because it signs as its user.
- Preserve the vendor `Authorization` when an alternate platform header authenticated the request. Strip platform credentials before upstream calls; never send vendor authorization to an MCP bridge.
- Python mirrors both Go programs, including credential format, grants, refresh locking and protocol.
- Android discovers the issuer only from the chosen API, without HTTP redirects, and allows only that HTTPS issuer and API auth paths inside its WebView. External sites remain external.

## Tenants

Every organization is a **tenant**, under the one **root** organization (`auth.ROOT_TENANT`, `"root"`; `orgs.parent` is `"root"` for every other, `None` for it). Nothing crosses tenants, except site admins: they see and control everything in every tenant, to look after the server. Check the tenant first, before roles, sharing or grants: `auth.same_tenant(identity, tenant)`, which is false for a missing tenant (fail closed), and true for a site admin whatever the tenant. On top of it, `access.can_view`/`can_control` and `fleet.allowed` answer yes for a site admin (private sessions, every machine feature), and `fleet.runs_containers` lets them manage containers anywhere. `access.is_owner` stays the owner's alone, so "delete all my sessions" and changing a session's sharing never reach other people's.

- **Users** (`users.tenant`, `Identity.tenant`): exactly one tenant each, set when made and never changed (`UserStore.update_user` refuses `orgs` that differ, `set_membership` refuses joining or leaving an organization). `Identity.orgs` is `(tenant,)`; teams are only that tenant's. `role` is per tenant: `Identity.admin` is an admin of their own organization; `Identity.site_admin` is an admin of the root, which takes only admins. Because a user's tenant never changes, anything stamped with it at creation stays correct.
- **Roles at the boundary**: `auth.SITE_ADMIN_ONLY` (server settings and everything under `/api/config`, restart, server stats, the access log, making and removing organizations) needs `site_admin`; `auth.ADMIN_ONLY` (which includes it, plus containers, adopting a provider, legal holds (`/api/holds`), `/api/orgs/*`, `/api/users/*`) needs `admin`, and the route then checks which organization: `auth.administers(identity, tenant)` (its admins, and site admins for the directory of any). Others answer 404, not 403.
- **Sessions**: the server-set tag `tenant` (in `access.SHARING_TAGS`, so clients can't set it), from `access.sharing_tags` (every launch and `/api/sessions`) and `Runtime.resolve_session` (implicit sessions). `access.can_view`/`can_control`/`is_owner` start with `in_tenant`. Requests, traces, chats, live events, terminals and MCP all go through those, and `/api/status` token totals add up only visible sessions (`Runtime.tokens`, per session).
- **Machines**: `Machine.tenant`, its first owner's, set in `Fleet.connect`, which refuses the same id from another user or tenant. `fleet.owns`/`allowed`/`can_manage` start with the tenant; grants (`checked_access`) only name the machine's own organization and its teams, and `granted` ignores any others. `removed_for`, `machine_for`, launch verification and tunnel attach check it too.
- **Backends** have no tenant column: `Fleet.backend_tenant` derives it from the machine (nobody's once the machine is gone), from the `org` option for a hosted `api` backend (`api_providers.owner`; none is the root), the root's for a machine type without a machine (from before machines), and `Fleet.SHARED` for the `anthropic` pass-through (site admins' Server settings; agents bring their own credentials). An `api` backend carries a key, so it isn't shared: `Fleet.api_tenants` (its own tenant, plus for a hosted one its `orgs`, `"*"` every tenant) decides, in `usable_by` and `routes/providers.py`; within its own tenant `teams` (`api_providers.for_teams`; none listed is everyone) limits it, except for that tenant's admins. Its tenant's admins manage it at `/api/orgs/{org}/providers` (`routes/api_providers.py`: `managed` checks `administers`, the tenant before anything else; a name another tenant uses is a `409` that doesn't say what it is; `orgs` only from site admins; `fallback` and `teams` only the tenant's own); site admins also at `/api/config/providers` (`SITE_ADMIN_ONLY`). Removing an organization removes its hosted providers and keys, its machines, usage limits and retention policy, and leaves its sessions tenantless (site admins only); removing a user removes their machines, provider accounts and own usage limits (`UsageLimits.remove_user`) and disowns their sessions and `launched_by` tags (`routes/auth.remove_org`/`remove_user` + `offboard`): a recreated name inherits nothing. Legal holds block removing the organization. The CLI (`agent-server user remove`) removes the account and its usage limits (database rows, no running server needed); machines, provider accounts and session ownership need the running server, so remove people in the console when they had any. `Fleet.usable_by(identity)` is the filter every backend lookup for a user takes: `Settings.backend(name, usable)`, `Settings.backend_for(..., usable)`, compat's `_backend` (so `X-AI-Proxy-Backend` can't reach another tenant's), `/api/agents`, `/api/models`, `/api/status`. Containers are reachable only through a visible machine (`routes/containers.py` `mine`). Backend names stay unique server-wide.
- **Migration** (`db/migrate.py` step 2, `_tenants`): each user to their first organization by id (admins in none to the root, members in none to `main`), teams of other organizations dropped, sessions and machines to their owner's tenant (ownerless ones to the root). Frozen in the step; don't make it call `auth.py`.

## Authorization invariants

`Runtime.resolve_session` enforces open-session control permission for every explicit agent session, including unscoped native `/api/*` headers. Do not rely only on middleware prefixes. Unscoped GET forwarding does not allocate a session. Issuer password checks share a normalized-account counter (hashed name, 30/600 seconds) across browser and device forms, in addition to the source-address counter (10/600 seconds).

- Nothing crosses tenants except for site admins, who see and control every tenant's sessions, machines and providers. Every new route that returns or changes a session, machine, backend or container checks the tenant (through the helpers above), and lists filter by it.
- Private sessions remain private from organization admins (not site admins); owners and `launched_by` control their sessions. Shared viewers control only with explicit control access.
- Clients cannot set server-owned tags. Narrowing sharing disconnects viewers. Shell sessions stay private.
- Machine owner always has its features; its tenant's admins implicitly have view/models/update only (`ADMIN_FEATURES`). Launch, terminal (shells) and MCP require their specific grants (site admins have them all) and the machine's toggles, which bind site admins too. Roots are checked server-side and again after resolving paths on the machine.
- The API owns account/directory mutations; the issuer is read-only (by `UserStore(readonly=True)`, and on PostgreSQL by its role's grants). Adding or removing all users never disables authentication.
- Bootstrap (`app.ensure_first_user`) runs on API process start, including loopback, unless accounts were ever written (meta `accounts_initialized`, set by every directory change and by the import of an old `users.json`; `UserStore.initialized()`) or the environment account is set: it adds `admin` (a site admin, in the root) and saves its password in `first-user-password`, the one account file left. Removing every user afterwards doesn't bring `admin` back. `create_app` never manufactures a test identity.

## Provider accounts

Subscriptions (`provider_accounts.py`) are not identities: never store one in `mesh_auth` or treat one as a sign-in. Their checks are separate from machine grants: a `launch` grant never lets someone use the machine owner's subscription (`for_launch`), assignments go only to the account owner's own machines, and `may_use` excludes admins (a subscription is personal). Site admins see metadata only. A managed token leaves the vault only through `deliver`, bound to a server-made grant for one launch on one assigned machine, once. `tests/test_provider_accounts.py` covers it.

## Usage limits

Limits (`usage_limits.py`, `routes/providers.py`) are an organization's: `PUT`/`DELETE /api/orgs/{org}/limits` need `administers(identity, org)` (and are in `ADMIN_ONLY` with the rest of `/api/orgs/*`), name only that organization's users (or `*`) and the providers it can use (its machines' backends and the shared hosted ones, plus the subscription kinds). `GET /api/orgs/{org}/usage` is for its members (`same_tenant`), who see only their own rows; another organization's answers 404. Usage is counted for a session's `launched_by` (else `owner`) in its `tenant` tag, both server tags clients can't set, so nobody can spend someone else's limit or dodge their own by tagging a session. `tests/test_usage_limits.py` covers it.

## Extending and testing

Add admin policy, session checks or machine-feature checks for each new route, document it in `docs/api.md`, and cover signed-out, wrong-user and role/grant failures. Public paths must be deliberately added, never inferred from an open session.

`test_oidc_issuer.py` exercises grants, PKCE, device approval, replay/revocation, service clients and hashed state. `test_db.py` covers the issuer's read-only accounts and the import of an older issuer's `issuer.sqlite3` and `signing-key.pem` (existing sign-ins stay valid). `test_oidc_api.py` covers mandatory auth and credential isolation. `test_oidc_browser.py` runs the real issuer through the API BFF. `test_quickstart.py` checks the quickstart's credentials against a real issuer and its Compose layout; `quickstart/tests/test_e2e.py` signs in against the running Compose stack. `test_client.py` runs Go (and, from `python/tests`, Python) against a real server and `create_auth_app` issuer. Permission suites use controlled introspection without weakening production middleware: `tests/oidc_helpers.py` swaps `Auth.client` for a mock introspection endpoint (`Issuer.issue`/`revoke`, `access_token`) and `authenticated_client` is a `TestClient` signed in as `test-admin`.

Operational configuration, endpoints and migration are in `docs/oidc.md`. Issuer outage, missing secrets, expired credentials and malformed metadata must surface as errors, never local-mode success.
