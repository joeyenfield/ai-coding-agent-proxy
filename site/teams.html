Controls in the open-source project

Decide who can do what.

Organizations, teams and sharing

Separate people and resources by organization. Share a session with a team or organization, with view or control access. Users belong to one organization; site admins can view and control private sessions across organizations.

Accounts and session sharing →

Machine grants and launch folders

Grant launch, terminal, model or MCP access separately. Remote execution also needs the machine’s switches and an allowed starting folder, checked again on the machine after resolving links. These are launch controls, not a filesystem sandbox for the agent.

Machine controls →

Per-person/provider usage limits

Set token limits for a person or a per-person default, by provider and time window. Reached limits block new sessions and model calls with 429. Calls already in flight finish and can exceed a limit; this is not a prepaid spending cap.

Enforcement and counting →

Recording policy and retention

Allow opt-in tracing, disable it or require it. Set separate lifetimes for traces, terminal output, request records and sessions. New sessions take a policy snapshot; later policy changes do not rewrite existing sessions’ policy.

Recording policies →

Legal holds

Hold an organization, person or session to pause scheduled retention deletion of covered recordings until release. Organization holds also pause audit expiry. Manual session deletion and clearing do not currently check holds. Treat holds as an incomplete legal-preservation control. Database backups, exported copies and bucket lifecycle rules need their own coordinated retention controls.

Retention and holds →

Audit verification and exports

Review recorded administrative changes, refusals and access to others’ recordings. Verify hash chains and signed checkpoints; export CSV/NDJSON or configure OTLP/HTTP, syslog, webhooks or blob exports. Protect external copies and verify delivery; the signing key lives in the server database.

Audit formats and integrity →

Authentication uses the project’s own agent-auth OIDC issuer. This does not establish integration with arbitrary enterprise identity providers. Entra ID, Okta, SAML, SCIM and MFA integrations are not verified here. Identity deployment →

Architecture and operations

Choose a deployment you can operate.

Agents execute on developer or fleet machines. Fleet machines initiate outward connections for their model servers and MCP bridges. The central server processes traffic, checks access and stores records. Hosted API and vendor-account traffic continues to the vendor.

Single server / Compose

Run the server and its separate sign-in service with PostgreSQL. Set your own secrets, API/issuer URLs, TLS and backups. The localhost quickstart is a trial configuration, not a production template to expose unchanged.

Compose and production setup →

Kubernetes / Helm

The repository chart offers a single deployment or deployments grouped by server role, with migrations, probes, autoscaling configuration and disruption budgets. Supply ingress, storage and secrets; optional operators must already be installed.

Helm values and prerequisites →

Multiple server roles

Split API, model gateway, MCP, interception, fleet, realtime and background jobs. Processes share PostgreSQL and Redis/Valkey, and reach one another on a private authenticated internal port. Route streaming and WebSocket paths to the right role.

Roles and routing →

Storage and operational signals

Keep recordings in the database or configure shared filesystem/S3-compatible blob storage. Use /health, /ready and internal Prometheus /metrics to monitor processes, streams, fleet sockets, write queues and audit export backlog. Keep the internal metrics port private.

Storage, probes and metrics →

Provider accounts

Know whose sign-in a task uses.

Subscriptions are provider-specific accounts assigned to machines, with health and usage observed by the mesh. They do not create a shared entitlement across people.

Credentials follow the provider’s model

Claude Code and Codex remain signed in on each machine; the mesh does not copy their sign-in files. Copilot can use a machine’s own sign-in or a supported managed fine-grained token. Managed tokens are encrypted under a separate vault key and delivered once to an authorized launch on an assigned machine, in the agent’s environment.

A machine receiving a token can use it. Assign only machines you trust; vendor terms and limits still apply.

Selection happens before a task

The planner filters permitted accounts and launchable machines, preferring available, then near-limit, then unknown sign-in state (if allowed). It then orders by account priority, requested agent order and lowest estimated percentage used. Throttled or exhausted accounts and accounts past their declared stop threshold are excluded.

Only the planning endpoint’s explicitly supplied local-model fallback agents are considered. Automatic account selection on a machine launch supplies no fallback list. No paid API is chosen automatically, and work is not moved mid-task. Recent usage writes can lag the account-state read. Usage covers mesh-observed traffic; remaining balance is an estimate against a declared limit, not the vendor’s meter.

A bounded pilot

Evaluate with your own acceptance criteria.

  1. Prove one useful workflow. Run the local quickstart, connect a provider and inspect a complete agent session. Check the agent/model combination you actually need.
  2. Review access and data. Create two test users and teams. Verify session visibility, revoked machine grants, allowed launch folders and an MCP selection. Choose capture, retention and hold policies using the data-handling guide.
  3. Exercise enforcement. Set a low token limit, inspect its refusal, create and release a hold, verify the audit chain and confirm an export arrives at your collector.
  4. Test an isolated deployment. Use the Kubernetes trial or production Compose guidance. Supply private secrets and TLS; test backups and restores, expired credentials, lost connections and upgrades.
  5. Measure before expanding. Record concurrency, latency, resource use, storage growth and recovery time under representative traffic. Resolve identity, security-review and operational gaps before broader adoption.
