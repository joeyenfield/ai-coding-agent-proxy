Capture policy

Metadata, bodies and terminals are different.

Request metadata

Model calls record session/request identifiers, agent, model, backend, endpoint, timestamps, sizes, status/errors, token counts and timings. Captured traffic may also record host, method and request kind. Some incomplete streams use token estimates, marked as estimated.

MCP POST calls are also request records. A session links them to its owner, project and sharing settings.

Prompt and response bodies

Full tracing defaults to opt_in per session. Organization policy, within server bounds, can set it to off or always. The session receives that policy at creation; later changes apply to new sessions. Account-traffic bodies have an additional intercept_bodies switch.

Traces can include code, prompts, replies and tool content. Sensitive headers and certain sign-in fields are filtered in interception, but bodies are not generally redacted. Live output can still be visible without saved traces.

Shared terminal output

A manual launch shares its terminal with --control; fleet launches use a shared terminal. Output is retained by default when shared, separately from full tracing. A policy can disable terminal_output persistence while viewers still see live output.

Terminal output can contain secrets printed by any program. Disabling traces alone does not disable terminal recording.

Operational and audit records

Access logs describe HTTP/WebSocket requests and outcomes. Audit events record actors, actions, targets and results for covered operations. They are separate from model traces; issuer sign-in logs also need collection by the operator.

Access controls and boundaries

Private sessions have explicit exceptions.

Sessions are private by default. Owners can share them with their team or organization, with separate view and control access. The person who requested a remote launch can access its session; the machine owner also owns that run. Site admins can view and control sessions across organizations, including private ones.

Sign-in and revocation

The built-in OIDC issuer supports browser sign-in with PKCE, device approval for clients and machines, and provisioned service clients. Roles and grants are checked at the API. Open connections recheck credentials periodically; revocation is not instantaneous on every stream.

Remote execution and tools

Machine grants, local switches and launch folders restrict who can start agents and shells. A running agent still has its operating-system user’s permissions. MCP access is selected per session and rechecks the launcher’s machine grant; tool permissions and remote services remain the tool operator’s responsibility.

MCP access and limitations →

Self-hosting means trusting the server operator and the machines you use. Application access rules do not prevent a database, host or backup administrator from reading stored data. The repository does not establish general enterprise federation, SAML, SCIM or MFA support.

Persistence and deletion

Know where each copy lives.

Recordings and retention

Settings, accounts, sessions and request records live in the server database: SQLite by default or PostgreSQL. Traces and terminal chunks can stay there or use configured filesystem/S3-compatible blob storage. Policies set separate lifetimes, counted from session activity; the worker deletes expired data hourly.

By default, traces, terminals, request records and sessions have no expiry; audit events default to 365 days, with a 90-day floor. Set an explicit policy for your deployment.

Holds and exported copies

Organization, person and session holds pause scheduled retention deletion of covered session data until lifted. Manual session deletion and clearing do not currently check holds. Do not rely on them as complete legal preservation. Only organization holds preserve the organization’s audit events. Backups, SIEM exports and independent bucket lifecycle rules are outside that deletion process; coordinate them so they do not defeat holds or exceed retention requirements.

Credentials and keys

Client and machine OAuth tokens live in separate local credential files; browser tokens use HttpOnly cookies. The issuer keeps grant/token hashes and its signing key in its own state. The server database holds generated secrets, including the capture CA private key and audit signing key.

Claude Code and Codex sign-in files stay on their machines. Managed Copilot tokens are encrypted in the database using an external vault key and delivered to assigned machines for authorized launches. API provider keys stay on the server: in an AI_PROXY_API_KEY_* environment variable or encrypted under the same vault key, bound to the provider’s address, and never shown, exported or sent to agents. MCP command configuration, environment and upstream headers remain on the sharing machine.

Audit integrity

Hash chains, append-only database checks and signed checkpoints let you verify recorded history. Export checkpoints and events to independently protected storage for stronger evidence. The application does not configure S3 Object Lock for you, and a database holding both records and signing keys is not an independent trust anchor.

Traffic and transport

The server sees traffic it processes.

Account-agent interception

Supported account agents use a loopback proxy that tunnels traffic to the central server over WebSockets. The server terminates TLS using its own CA, then makes a separately verified TLS connection to the vendor. The launcher adds that CA to the launched process tree’s trust, not the system trust store.

It can see sensitive content and credentials in transit. Private/reserved destinations are refused; configured pass-through hosts are tunnelled without decryption and recorded as connections only. This is not end-to-end encryption between agent and vendor.

Account capture and redaction boundaries →

Local models and external vendors

Fleet machines open outbound connections and tunnel model and MCP requests to local services. Model servers and the MCP bridge can remain on loopback. Hosted Anthropic and account-agent requests go to the vendor; URL-based MCP tools can also call external services. Hosted API providers are reached only at public addresses, pinned to the address checked and never through a redirect; a private gateway needs the operator to allow its host.

Choosing a local model does not stop the agent’s other network activity. Older backends, exposed containers and custom provider addresses need separate network review.

Architecture and request paths →

Deployment responsibilities: configure HTTPS/WSS, exact callback and console origins, private database/Redis/internal ports, TLS on networked storage connections, secrets management, storage encryption and protected backups. Restrict model ports and test recovery. The local demo’s known credentials and loopback HTTP are for one-computer trials.
