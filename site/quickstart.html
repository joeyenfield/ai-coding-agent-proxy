Steps 2 to 9

From sign-in to an answer.

The rest happens in the console, on one machine. Every screenshot is the real one-container quickstart, started fresh.

  1. 2Sign in

    Open localhost:19999. Type localhost exactly: sign-in only accepts that address. Continue to sign in takes you to the sign-in service on port 20000.

    Sign in as admin with the password the container printed (docker logs mesh)the installer printed. It was made for this install alone, and you can change it under your name in the console.

  2. 3Check your machine

    Open All machines. my-machine is the container itself, already Online: it signed itself in when it started.Your computer is there under its own name, already Online. The screenshots below are from the one-container version, where it is called my-machine.

  3. 4Start a model server

    Open the machine, then Providers. Ollama is installed in the container but not running: choose Start.It lists the model servers on your computer. Start the one you have, or install one (Ollama from ollama.com; llama.cpp installs from this page). Within a minute it is found on the machine.

  4. 5Add my-machine's model server as your own provider

    Model servers belong to the machines that run them, and an admin adds each one once. On my-machine, open Providers: it found one on port 11434, Not a provider yet.

    Open it and choose Add as a provider. It is now a provider of your own: agents reach it through the server and my-machine's own connection, with no port to publish.

    Your provider, not ours. Ollama is only the model server this quickstart happens to run. A provider is whatever you bring: llama.cpp, Strata, Docker Model Runner, LM Studio, vLLM or SGLang on a machine show up on this tab the same way, and a hosted API (OpenAI, Anthropic, DeepSeek, OpenRouter) is added with its key on Providers. Providers, in the docs →

  5. 6Find a model and pull it

    The model server starts empty, and nothing downloads by itself. Open Find and pull, keep Ollama library, search for qwen3.

    Each family lists its sizes; tools is what coding agents need. On a CPU, pick something small: Pull 1.7b downloads 1.3 GB and answers in seconds.

    When it's done, it's on the Models tab, with the settings the server uses for it.

  6. 7Start Qwen Code on my-machine

    Choose Start an agent. Pick my-machine and Qwen Code. Own provider is already the one you added, the folder is /workspace and the model is the one you pulled. Enable Capture full request and response payloads, then choose Start on my-machine.

    It starts in a terminal shared with the server, and the console opens it: watch it and type into it from any device.

  7. 8Ask it something

    Type What model are you? in Message for the agent and choose Send. The first answer is the slowest: the model loads on the first request, a minute or two on a CPU.

  8. 9See what it sent

    Open Requests and select a successful model call from your session. Choose Full screen to inspect it. Conversation shows the captured prompt and reply; Request shows the request JSON. Payload capture must be enabled before the call. The example below uses a captured Qwen Code call from the one-container demo; the inspector works the same way in each setup.

Steps 2 to 9

From a password in a log to an answer.

This level has no known password and no machine that lets itself in: you read one from a log and approve the other, as on a real server. Every screenshot is the real Helm quickstart on a local cluster.

  1. 2Forward the two ports

    Nothing in the cluster is published. Forward the console and the sign-in service to your computer, in a terminal you leave open:, each in a PowerShell window of its own that you leave open:

    kubectl -n mesh port-forward svc/mesh-agent-mesh 19999:19999 &
kubectl -n mesh port-forward svc/mesh-agent-mesh-auth 20000:20000
    kubectl -n mesh port-forward svc/mesh-agent-mesh 19999:19999
kubectl -n mesh port-forward svc/mesh-agent-mesh-auth 20000:20000

    A port-forward ends when its pod restarts: run it again if localhost:19999 stops answering.

  2. 3Read the password and sign in

    Nothing here has a known password. The server made an admin account on its first start and printed the password in its log, that one time only:

    kubectl -n mesh logs deploy/mesh-agent-mesh -c agent-server | grep -i password
    kubectl -n mesh logs deploy/mesh-agent-mesh -c agent-server | Select-String password

    Open localhost:19999 (type localhost exactly), choose Continue to sign in, and sign in as admin with that password.

  3. 4Let the machine in

    The machine signs in the way any computer does: with two device codes, one for agent-machine and then one for agent. Its log shows one at a time, and a new one when a code runs out after ten minutes:

    kubectl -n mesh logs deploy/quickstart-machine -c machine

    Open Machines › Approve a device, type the newest code and choose Continue.

    The console shows what asked before you decide. Choose Approve. The log then shows the second code: approve it the same way.

    Within a minute k8s-machine is Online on All machines. It belongs to whoever approved it.

Three values files ship with the chart. Small team is one pod with SQLite, enough for a team trying it in earnest. The two scaled forms run a Deployment per role on PostgreSQL and Redis, on managed cloud services or on your own hardware. Pick one in the box.

Steps 2 to 7

From DNS to a fleet.

Most of the work comes before the install command. There are no screenshots here: the console is the one the other levels show, at your own address.

  1. 2Host names, TLS and routing

    Point two HTTPS host names at the cluster: server.host for the API (say api.example.com) and auth.host for the sign-in service (auth.example.com). Keep them subdomains of one site: the sign-in cookie depends on it.

    Route them with a Gateway API Gateway that has listeners for those hosts (routing.gatewayAPI.gatewayRef), or an Ingress controller (routing.ingress).

  2. 3Your own secrets

    The chart never takes database or Redis URLs in its values: they come from Secrets you make. The app Secret holds the token pods use with each other, the secret the server and the sign-in service share, and the keys that encrypt stored tokens:

    kubectl create namespace mesh
kubectl -n mesh create secret generic mesh-app \
  --from-literal=internal-token="$(openssl rand -hex 32)" \
  --from-literal=oidc-introspection-secret="$(openssl rand -hex 32)" \
  --from-literal=vault-keys="$(agent-server vault key)"

    Leave the app Secret out and the chart generates the first two once and keeps them across upgrades. For the scaled forms, add Secrets with your PostgreSQL and Redis URLs; the README lists their keys.

  3. 4The database

    Small team needs nothing here: SQLite lives on the chart's volume. To use PostgreSQL instead, follow the scaled steps.Create two roles and two schemas in your PostgreSQL, one each for the server and the sign-in service, as server/docker/postgres-init.sh does. With CloudNativePG the chart creates them for you. A migration Job runs before each upgrade.

  4. 5Install the chart

    From a checkout of the repository, run the command for the size you chose in step 1, with your own host names. The chart migrates the database first, then starts each role.

    When it finishes, kubectl -n mesh get pods shows every pod Running, and the chart's notes say what to do next.

  5. 6Sign in and add your people

    The chart's notes print how to read the first admin password from the server's log. Open your API host name, sign in, change that password, and add your people under Organizations, or connect your own sign-in.

    Accounts, organizations and teams →

  6. 7Bring your machines and your providers

    On each computer that should run agents or serve models, install agent-machine from the console's Downloads page and sign it in:

    agent-machine login https://api.example.com
agent-machine start

    Approve its code on Machines › Approve a device, or hand out a setup code. Then add each machine's model server as a provider of your own, and any hosted API with its key, exactly as in the other levels.
